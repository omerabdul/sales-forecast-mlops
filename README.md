# Sales Forecast Prediction — MLOps Pipeline

An end-to-end MLOps pipeline that predicts total sales revenue for a
product/store combination, automated with **GitHub Actions** and hosted on
**Hugging Face** (dataset repo, model repo, and a Docker-based Space for the
live app).

```
register-dataset  →  data-prep  →  model-training  →  deploy-hosting
```

---

## Business Context

A sales forecast predicts future sales revenue based on historical data,
industry trends, and the status of the current sales pipeline. Businesses
use it to estimate weekly, monthly, quarterly, and annual sales totals. An
accurate forecast improves decision-making, reduces sales pipeline and
forecast risk, cuts down time spent on territory planning, and gives the
supply chain team a reliable basis for procurement.

## Objective

Build an automated MLOps pipeline with CI/CD that trains a model on
historical product/store sales data, tracks experiments, and continuously
redeploys an app that produces sales forecasts — with minimal manual
intervention after setup.

> **Scope note:** the dataset is a *cross-sectional* extract — one row per
> product-per-store, with a single revenue total, and no date/time column.
> The model predicts **a single sales-total figure per product/store**, not
> a true week-over-week or month-over-month time series. The app derives
> weekly/monthly/quarterly figures by evenly dividing that total — a
> planning convenience, clearly labeled as such, not an independent forecast
> per period.

## Data Description

Source file: `mlops/data/sales.csv` (the **SuperKart** extract — 8,763 rows,
4 stores × ~2,200 products each).

| Column | Description |
|---|---|
| `Product_Id` | Unique product identifier (two letters + a number). Dropped before modeling — no standalone predictive signal. |
| `Product_Weight` | Weight of the product. |
| `Product_Sugar_Content` | `Low Sugar` / `Regular` / `No Sugar`. Raw data also contains `reg` as a messy variant of `Regular`, standardized during preprocessing. |
| `Product_Allocated_Area` | Ratio of the product's allocated display area to the store's total display area. |
| `Product_Type` | `Meat`, `Snack Foods`, `Hard Drinks`, `Dairy`, `Canned`, `Soft Drinks`, `Health and Hygiene`, `Baking Goods`, `Breads`, `Breakfast`, `Frozen Foods`, `Fruits and Vegetables`, `Household`, `Seafood`, `Starchy Foods`, `Others`. |
| `Product_MRP` | Maximum retail price of the product. |
| `Store_Id` | Store identifier. Only 4 distinct stores (`OUT001`–`OUT004`) — kept as a categorical feature since it captures store-specific baseline performance. |
| `Store_Establishment_Year` | Year the store was established. Converted to `Store_Age` (years in operation) during preprocessing. |
| `Store_Size` | `High` / `Medium` / `Small`. |
| `Store_Location_City_Type` | `Tier 1` / `Tier 2` / `Tier 3`. |
| `Store_Type` | `Departmental Store` / `Supermarket Type1` / `Supermarket Type2` / `Food Mart` (no space before the digit). |
| `Product_Store_Sales_Total` | **Target.** Total revenue generated by that product at that store. |

> Category labels don't always match plain-English wording — e.g.
> `Store_Size` uses `Small` (not `Low`), and `Store_Type` has no space
> before the digit. Every script uses the raw labels exactly as shown above.

## Pipeline Stages

| Stage | Script | What it does |
|---|---|---|
| Register dataset | `mlops/model_building/data_register.py` | Uploads the raw `sales.csv` extract to a Hugging Face **dataset** repo. |
| Data prep | `mlops/model_building/prep.py` | Cleans the data, standardizes sugar labels, imputes missing values, engineers `Store_Age`, splits train/test (80/20, no stratify — the target is continuous), uploads the splits back to Hugging Face. |
| Model training | `mlops/model_building/train.py` | Builds a `StandardScaler` + `OneHotEncoder` + `XGBRegressor` pipeline, tunes hyperparameters with `GridSearchCV` (scored on RMSE), tracks runs and metrics (RMSE, MAE, R²) in MLflow, and uploads the winning model to a Hugging Face **model** repo. |
| Deploy hosting | `mlops/hosting/hosting.py` | Pushes `mlops/deployment/` (Streamlit app + Dockerfile + requirements) to a Hugging Face **Space**, which rebuilds and redeploys the live app. |

Every stage runs automatically, in this order, whenever `.github/workflows/pipeline.yml` fires on a push to `main`.

## Tech Stack

- **Modeling:** scikit-learn, XGBoost
- **Experiment tracking:** MLflow (+ ngrok for local dev tunneling)
- **Storage / registry:** Hugging Face Hub (dataset repo, model repo)
- **App:** Streamlit, hosted on a Hugging Face Space (Docker SDK)
- **CI/CD:** GitHub Actions

## Prerequisites

You'll need three credentials before running the pipeline:

1. **GitHub Personal Access Token (classic)** — scopes: `repo`, `workflow`.
   Create at GitHub → Settings → Developer settings → Personal access tokens.
2. **Hugging Face access token** — **write** access. Create at
   [huggingface.co/settings/tokens](https://huggingface.co/settings/tokens).
3. **ngrok authtoken** *(optional, for local MLflow experimentation only)* —
   from [dashboard.ngrok.com/authtokens](https://dashboard.ngrok.com/authtokens).

The Hugging Face token must be available in **two** places:
- As a Colab secret (`HF_TOKEN`) if you're setting the project up from the
  companion notebook.
- As a **GitHub Actions repository secret** named `HF_TOKEN` (Settings →
  Secrets and variables → Actions), since the pipeline authenticates with it
  when running on GitHub's servers.

## Getting Started

The easiest way to stand this project up from scratch — creating the
GitHub repo, writing every script, wiring up secrets, and pushing
everything — is the companion notebook, **`Solution_Notebook_Sales_Forecast_MLOps.ipynb`**.
Open it in Google Colab and run it top to bottom; it walks through each
prerequisite and configuration step in order.

If the repository already exists (e.g. you're just cloning this project):

```bash
git clone https://github.com/<your-username>/sales-forecast-mlops.git
cd sales-forecast-mlops
pip install -r mlops/deployment/requirements.txt
```

Add your `sales.csv` file to `mlops/data/`, add the `HF_TOKEN` repository
secret, then push to `main` — the Actions pipeline takes it from there.

## Running Locally (single stage)

Each stage can also be run standalone, with `HF_TOKEN` set in your
environment:

```bash
export HF_TOKEN=hf_xxx...
python mlops/model_building/data_register.py
python mlops/model_building/prep.py
python mlops/model_building/train.py
python mlops/hosting/hosting.py
```

To run the app locally instead of via a Space:

```bash
streamlit run mlops/deployment/app.py
```

## Deployment

No manual deployment step is required. The **deploy-hosting** job pushes
`mlops/deployment/` to your Hugging Face Space on every pipeline run, which
rebuilds the Docker image and redeploys automatically. Once the pipeline
finishes, the live app is at:

```
https://huggingface.co/spaces/<your-hf-username>/<your-space-name>
```
